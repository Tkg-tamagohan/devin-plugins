# テストは仕様から作成し、ID を振って結果を表で報告する

テストコードを書くときは実装ではなく文書を根拠にし、テストケースには ID を振って結果を表で報告する。
実装から期待値を逆引きしたテストは、実装のバグまで正しい挙動として固定してしまう。

## 仕様や要件から作成する

- テストは実装コードの挙動をなぞるのではなく、要件定義や仕様書などの文書を根拠に作成する。
- 呼び出し回数など実装詳細への厳密な検証は、仕様に由来する値だけに限る(仕様と無関係な正当な変更でもテストが壊れるため)。
- 失敗を確認するテストは、エラーの有無だけでなくどの対象が失敗したかを識別できる検証にする(対象外の経路が出したエラーでも通ってしまうため)。
- 複数の対象を順に処理するコードは、先の対象が失敗したとき、仕様どおりに残りの対象への処理を続けるか、中断することを検証する。
- タイムアウトや期限切れで期待した事象を観測できなかった場合は失敗として扱う。
- 非同期待機、中断、失敗注入、有界チャネル、複数レーンのテストは壁時計の `sleep` ではなく対象レーンや発火状態の同期バリアで確定させてから検証し、同期モックによるランタイム飢餓を防ぐ(細目は `shared-skills:systems-pre-pr-audit` を参照)。
- モジュール単体だけでなく、上位ランタイム(定期タスクや IPC 入口)から実呼び出しされている結合点と本番相当の境界まで検証対象に含める。
- 実装と文書が矛盾しているときは、どちらを正とするか自分で推測せず、ユーザーに確認する。

## ID を振って結果を表で報告する

- テストケースを作成するときは、対象を表す短い識別子と連番の組み合わせ(例: `AUTH-01`)で ID を振って管理する。
- テスト実施後は、テスト項目一覧とテスト結果を表にまとめて表示する。
- 失敗したケースは追加で抽出し、改善案とあわせてユーザーに提示する。

## 対象外

- テストコードの作成も実施も伴わない作業
