# Devin Review 指摘のトリアージと対応

Devin Review が PR に投稿した指摘は、修正するか根拠を説明するかを一件ずつ判断してから対応する。
「指摘だから直す」と一律に扱わない。
意図的な挙動を仕様なしに変えると、レビューが仕様を上書きする形になる。

## 責任範囲の境界

- **テストの作り方**：修正に添える回帰テストの ID 規約と結果報告の形式は `test-conventions` に従う。
- **文書との矛盾**：実装と文書の扱いが食い違う指摘を含むとき、どちらを正とするかは `test-conventions` と AGENTS.md の「仕様や計画の文書がある作業ではそれを正とする」に従う。

## 手順

1. 各指摘を仕様の正（要件定義書、決定記録、実装計画など）と照合し、「実バグと文書の齟齬」と「意図的挙動」に分類する。
   - 判断の根拠を指摘ごとに記録する。
2. 実バグは修正して回帰テストを ID 採番で追加し、文書の齟齬は文書側を修正する。
3. 意図的挙動と判断した指摘には、その挙動を選んだ根拠（仕様決定の ID、トレードオフの説明）をスレッドに返信する。
4. 修正はテストが緑になってから、`Devin Review 対応: <要約>` の形式のコミットにまとめて push し、無関係な変更を混ぜない。
5. 修正または説明が完了した指摘に限り、各スレッドへ `git_comment_on_pr` で返信し、`resolve_thread_id` で解決する。
   - 説明だけで閉じる指摘にも返信を残す。
   - 判断待ちの指摘はユーザーの回答と対応が終わるまで解決しない。
6. 修正すべきか意図的か判断できない指摘、ユーザーの指示と矛盾する指摘（直すと指示を巻き戻すもの）は、自分で決めずにユーザーへ判断を仰ぐ。

## 原則

- 指摘の分類（修正／説明／要確認）を一覧できる形にし、ユーザーが分類を覆せるようにする。
- 返信は指摘ごとのスレッドに対して行い、まとめて一件のコメントで済ませない。
- 低重大度の nit や大掛かりな対応が要る非クリティカルな指摘は、勝手に大きな変更で応えず、対応要否をユーザーに確認する。
- 指摘は修正 push のたびに新スレッドや同一スレッドへの再掲(「Edited to」形式)で複数ラウンド追加されうるため、全スレッドを解決した後も、終了判定の前に新着通知を確認する。
- push 後に Devin Review のチェックが pending のまま残ることがあるが、required でなければ表示ラグなので、マージ可否の判断には使わない。
