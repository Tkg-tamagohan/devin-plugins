# ルールとスキルの作成指針

devin-plugins に置くルールとスキルは、Devin のセッションに読み込まれてコンテキストを消費する。
常時読み込まれるものが増えるほど、どのセッションでも無関係な指示を抱えることになり、必要なときにだけ読まれるものが細かく割れるほど、読むべき状況の判定が増えて取りこぼしが起きる。
この指針は、その両方を避けるために、置き場所、粒度、構成、運用の基準を定める。

## 置き場所の判断

このプラグインには三つの置き場所があり、読み込まれ方が異なる。

- **AGENTS.md**：全セッションに常時読み込まれ、本文の全体が毎回コンテキストに入る。
- **rules/<name>.md**：`trigger: model_decision` の rule で、セッションには description だけが常時示され、モデルが状況に合うと判断したときに本文を読む。
- **skills/<name>/SKILL.md**：スキルで、名前と description が常時示され、呼び出されたときに本文と補助ファイルを読む。

このほかに、作業対象リポジトリ内の `.devin/skills/` や AGENTS.md という置き場所がある。
そのリポジトリの事情に依存する内容は、共有プラグインではなくそちらに置く。

置き場所は次の表の問いに上から順に答え、最初に当てはまった行を採用する。

| 問い | 置き場所 |
| --- | --- |
| 特定のリポジトリの構成や手順に依存するか | 作業対象リポジトリ内の `.devin/skills/` または AGENTS.md |
| どの種類のセッションでも起こりうる判断についての、短い制約か | AGENTS.md の一節 |
| 特定の作業種別(テスト、UI、依存追加など)でだけ守るべき制約で、状況を一文で言えるか | `rules/` |
| 手順、背景知識、テンプレートなど、従うのに数十行以上を読む必要があるか | `skills/` |

AGENTS.md に置くかどうかの境目は「作業種別に依存するか」にある。
推測を推測と明記する、依頼範囲に限定する、といった制約はコード変更でも文書作成でも同じように働くので AGENTS.md に置く。
一方、テストの作り方や UI の確認手順は、その作業をしないセッションには無関係なので rule にする。
rule の description は常時示されるため、必要なセッションでは読まれ、無関係なセッションでは本文の分だけコンテキストを節約できる。

rule と skill の境目は「制約か手順か」にある。
rule は「何をすべきか、してはならないか」を述べ、手順は状況を検出したあとの数ステップにとどめる。
手順が長くなる、テンプレートや NG と OK の対比例が必要になる、複数の節に分かれる、のいずれかに当たれば skill にする。
制約と手順の両方が必要なら、制約を rule に、手順を skill に分け、rule から skill を名前で参照する(`register-to-devin-plugins` と `plugin-authoring` の関係)。

## 粒度の基準

一ファイル(AGENTS.md では一節)に一トピックを置く。
トピックの単位は、見出しを命令形の一文で言い切れる範囲とする。
「テストは仕様から作成し、ID を振って結果を表で報告する」のように、一文に二つの動作が入ってもよい。
問うのは、同じ状況で同時に守るべき内容かどうかである。

統合と分離は次の目安で判断する。

- **統合する**：二つのファイルの description が同じ状況を指しているなら、一つにまとめる。
  - 同じ状況で片方だけ読まれる状態は、取りこぼしの原因になる。
- **分離する**：description に「または」で異なる状況を並べたくなり、かつ本文の節がその状況ごとに分かれているなら、分ける。
  - ただし分けた片方が 10 行に満たないなら、分けずに「対象外」で範囲を示す。
- **分離を保留する**：将来分かれそうでも、現時点で片方の事例がなければ分けない。
  - 事例が出たときに分ける(`windows-blueprint` の「スナップショットビルド失敗の調査」節は、Windows に依存しないが、他プラットフォームの事例が出るまで同じスキルに置く)。

大きさの目安は、AGENTS.md の一節が 5 行以内、rule が 30 行以内、skill が 200 行以内である。
超えたら、分割するか、参照用の内容を補助ファイルに出す。
文体規範のように多数の項目からなる参照文書は、単一トピックであれば 200 行を超えても分割しない。

他のファイルにある内容は繰り返さず、名前で参照する。
`requirements-definition` の「責任範囲の境界」節が範であり、委ねる先と委ねる理由を一行ずつ書く。
AGENTS.md の常時ルールは全スキルの前提なので、スキル本文で繰り返さない。

## 構成の型

三つの置き場所には、それぞれ決まった型がある。
型を揃えることで、読み手は見出しだけで内容の位置を予測できる。

**AGENTS.md の一節**：`## 命令形の見出し` の下に箇条書きを置く。
最初の箇条で制約を述べ、必要なら理由を一箇条添える。
手順や例は書かない。

**rule**：frontmatter(`trigger`、`description`)、`# 命令形の見出し`、導入(何をどうするかと理由を二、三文)、`## 手順`、`## 対象外` の順に書く。
「対象外」は省略しない。
適用しない状況を書くことで、モデルが description だけで判断するときの誤適用を防ぐ。

**skill**：frontmatter(`name`、`description`)、`# 名詞句の見出し`、導入(いつ使うか、ゴール)、必要なら `## 責任範囲の境界`、本文の節、必要なら `## 原則` の順に書く。
本文の節は、手順なら番号付きリスト、知識なら見出しごとに一トピックとする。
NG と OK の対比が有効な場面では、コードブロックで並べる(`windows-blueprint` の書き方)。

テンプレートは `rule-template.md` と `skill-template.md` にある。
テンプレートの複写と README 収録一覧への記帳は `scripts/new_entry.py` が行う。

## description の書き方

description は、モデルが本文を読むかどうかを決める唯一の材料である。
本文の要約ではなく、読むべき状況を書く。

- **rule の description**：「〜するとき」で状況を書く。
  - 複数の状況があるなら「、または」でつなぐが、三つを超えるなら分離を検討する。
- **skill の description**：扱う内容の列挙、「〜するときに使用する」で使う状況、委ねる先(「〜は <skill名> に委ねる」)の順に書く。
  - 委ねる先を書くことで、近い領域のスキルとの取り合いを防ぐ。

状況は、作業の種類(テストを書く、依存を追加する)や成果物の種類(要件定義書、blueprint)で特定する。
「品質を上げたいとき」のように、どのセッションにも当てはまる書き方は避ける。

## 命名

ファイル名とディレクトリ名は小文字英数字と `-` のみとし、skill では frontmatter の `name` と一致させる。
rule は求める振る舞いか対象を表す語(`ui-mock-first`、`library-license`)、skill は扱う領域を表す語(`windows-blueprint`、`requirements-definition`)にする。
改名するときは、他ファイルからの参照(`shared-skills:<name>` の記述、README)を同じ PR で更新する。

## 文体

本文は `japanese-tech-writing` の規範に従う。
ルールとスキルでは、これに次を重ねる。

- 見出しと制約は命令形で書き、理由は一文添える。
  - 「必ず」「絶対に」のような強調で従わせようとせず、「対象外」で範囲を確定する。
- モデルが差分を読むときに変更点が行単位で追えるよう、一文一行で書く。
- 例は実際に起きた事象から採り、起きていないことを例として書かない。
- リポジトリ構造や外部サービスの状態に依存する記述を持つファイルは、執筆時点の対象バージョンを明記する。
  - 依存する記述が多いファイルでは前提を「構成の現在地」のような節へ分離し、数行のファイルでは該当行への付記で済ませる。
  - 陳腐化したとき監査で検出しやすくなる。

## 変更の運用

`.devin-plugin/plugin.json` の `version` は、追加と修正でパッチを、既存ファイルの移動、改名、削除を含む変更でマイナーを上げる。
バンプは `scripts/new_entry.py` の scaffold または `bump` が差分から判定して付ける。
利用側は再インデックスで新しい版を取り込むため、変更の種類がバージョンから読み取れる状態にしておく。

追加のたびに、既存ファイルとの重複を `rg` で確認する。
rule が 10 件を超えたら、description が同じ状況を指しているものがないかを見直す。
見直しの結果は、統合や分離の判断理由とともに PR 本文に残す。

## チェックリスト

作成、変更した内容を PR に出す前に点検する。

- [ ] 置き場所を判断表で決め、判断理由を PR 本文に書いた
- [ ] 既存ファイルと重複する内容がない(重複するなら参照に置き換えた)
- [ ] 見出しが命令形(rule、AGENTS.md)または名詞句(skill)の一文になっている
- [ ] description が読むべき状況を一文で特定している
- [ ] rule に「対象外」がある
- [ ] ファイル名、ディレクトリ名、frontmatter の `name` が一致し、小文字英数字と `-` のみである
- [ ] 大きさの目安(AGENTS.md の一節 5 行、rule 30 行、skill 200 行)に収まる、または超える理由がある
- [ ] `plugin.json` の `version` を変更の種類に応じて上げた
- [ ] README の構成の説明を追随させた
