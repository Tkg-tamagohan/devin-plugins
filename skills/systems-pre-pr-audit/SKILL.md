# 常駐システムと複数モジュール境界の PR 前監査

静的検査と単体テストの通過後、PR を作成または更新する前に、モジュール境界で起きやすい競合、抜け漏れ、過負荷を点検する。
レビュー前の自己検証や並列子セッションの最終確認基準としても使う。

## 責任範囲の境界

- **テストの一般方針**：仕様準拠のテスト設計と結果報告の形式はルール `test-conventions` に委ね、本スキルでは非同期ランタイム特有の同期と飢餓防止の細目だけを補う。
- **CI ワークフロー設計**：ジョブ分割とパス判定は `github-actions-ci` に委ねる。
- **文書とコードの全面監査**：リポジトリ全体の構造整理は `repo-drift-audit` に委ねる。
- **Windows シェル実行罠**：PowerShell の引用と文字コードは `windows-cli-pitfalls` に委ねる。

## 有界チャネルと停止ドレイン

1. 生産側コールバックと有界チャネルの間に無制限キュー（`unbounded_channel` 等）を挟まない。
   前段が滞留すると後段の容量上限とドロップ件数計測が無効になるため、センサーや生産側から直接有界送信境界へ渡す。
2. チャネル `close()` はフラグ更新だけでなく下層の受信クローズまたは待機中送信者の起動を伴わせ、待機中タスクが後から挿入した項目も確実にドレインする。
3. 通常停止では停止要求フラグで残余イベントを破棄せず、OS や SDK のセッション停止 API によるバッファ排出を完了してからパイプラインを閉じる。
4. 停止待機で `tokio::task::spawn_blocking(move || jh.join())` を使わない。
   予算超過後もブロッキングプール上のタスクが残って Tokio `Runtime::drop` が無期限ハングするため、スレッド内の RAII `Drop` ガードから `oneshot` で完了通知を送る。
   待機側は `timeout` で非ブロッキング待機して完了確認時だけ `join()` し、予算切れ時はスレッドをデタッチする。
5. スレッド内クロージャの Drop 順序に注意し、RAII 通知ガードの宣言より後でキャプチャ所有値（`Arc<RwLock<...>>` 等）をローカルへ再束縛して所有資源が通知より先に解放される順序を保証する。
   また、`in_flight` の `compare_exchange` 成功直後にキャンセルフラグを再確認し、停止競合時の後発スレッド起動を防ぐ。
6. ワーカーが停止予算内にチェックポイントを終えられない場合は、外部補助スレッドの終了待機より先に DB のチェックポイント（`wal_checkpoint(TRUNCATE)` 等）を実行する。
7. HTTP だけでなくファイルやストリーム（UNC/SMB 共有やパイプ等）の有界読み取りでも固定チャンク単位（例: 64 KiB）で読み取り、各反復前後および `ErrorKind::Interrupted` 再試行前にキャンセルを確認する。
8. 二段有界キュー（一次 FIFO キューと満杯時集約マップ）では、一次キュー部分ドレイン後の投入前に両層を横断して重複確認する。
   あわせて、集約マップでの同一対象上書き発生回数をカウンタとレート制限付き警告ログで可観測化する。

## 時系列と起動時スナップショット整合

1. 優先度レーン分離や非同期遅延によりイベントが追い越しうる経路では、処理時の最新 ID ではなくイベント発生時刻を含む時間窓で帰属先を引く。
2. 時刻をミリ秒等へ丸めて検索する際、同一単位内で ID 再利用が起きうる場合は、作成時の高分解能カウンタや単調識別子を第 2 ソートキーへ加える。
3. 起動時のスナップショット取得 API は、列挙失敗（`Err`）と正常な空一覧（`Ok([])`）を戻り値で区別し、取得失敗時に既存の継続稼働行を一括終了扱いへ倒さない。
4. ストリーム開始後にスナップショットを統合する場合は、次の 4 点をセットで検証する。
   - 起動前セッションの照合候補はストリーム開始前に確定し、開始後の新規エントリを誤終了させない。
   - 後着の古いスナップショットを破棄する際は、推定終了時刻を永続層へも伝播させる。
   - 子イベント先着後に親や補助メタデータが補完された場合、親依存ルールの再評価を行う。
   - 同一個体の重複観測では、既に発火済みのルールを二重に保留アラート化しない。
5. IPv4 と IPv6 のデュアルスタックなど独立した系列の履歴キャッシュでは、単一タイムスタンプを共有せず系列ごとに最新時刻を管理する。
   IPv4 射影 IPv6 等の同値表現は参照関数の先頭で正規化し、遅延応答で既存エントリの新しい時刻や、別キーの最新マッピングを後退させない。
6. 元プロセス終了で一時エントリが消去されたあとも共有 IP に別の有効遮断ドメインが残る経路では、単一クエリ名ではなく全ドメイン横断の最新マップを参照して有効ブロックの誤削除を防ぐ。
7. 非同期イベントの保留（park）判定、早期解除判定、および最終処理判定で同一の鮮度窓（例: 60 秒）と有効性述語を用い、非対称による猶予窓の素通りや誤早期解除を防ぐ。

## 永続化、トランザクション、クエリ計画

1. メモリ上の未フラッシュバッチを取り出して DB トランザクションへ書いた後、`?` で早期リターンする全経路でバッチ復元を保証する。
2. 数千件単位の TTL パージや一括削除はバッチ単位で書き込みロックを解放し、各バッチ境界で停止要求を監視して終了タイムアウト内にチェックポイントへ譲る。
3. `WHERE key = ? AND ts <= ?` 型の検索には `(key, ts DESC)` の複合インデックスを張り、`EXPLAIN QUERY PLAN` をテストで検査する。

## 重複抑止、ホットパス複製、認可とタイムアウト

1. 重複抑止キーの粒度が粗すぎて同プロセス内の別ペイロード（スクリプト本体等）を取りこぼさないか点検する。
2. ホットパスでエントリを引く際は、発火履歴等の成長するコレクションを含む構造体全体を `.clone()` せず、必要な文字列や ID だけを複製する。
3. 新設した状態変更や監査報告系の IPC/RPC ハンドラすべてに、既存コマンドと同等の呼び出し元認可を適用する。
4. IPC サーバでは同時接続上限、フレーム長上限、読み取りタイムアウトに加え、応答を読み取らないクライアント向けの書き込みおよびフラッシュタイムアウトを設定する。

## 非同期テストの同期と飢餓防止

1. 非同期待機、中断、失敗注入、有界チャネルのテストでは、壁時計の `sleep` で済ませず対象条件の発火状態（`Poll::Pending` 到達や処理途中のバッチ境界など）を同期して確定させてから後続を検証する。
2. 優先度レーン分離や複数キュー構成では、別レーンのイベントや名称から推測した件数 API を完了バリアにせず、対象レーンの処理カウンタ増分や実体確認済みの状態遷移で同期する。
3. マルチスレッド非同期ランタイム上で同期ブロッキングモック（同期バリアやスリープ等）を使うテストは、ランタイム種別ガード付きの `block_in_place` 等でタイマードライバ飢餓を防ぐ。

## PR 本文照合と結合確認

- 実装を変更した直後に新設または更新する PR の本文は、計画書や記憶から書かず `git diff <base>..HEAD` で提供範囲とフォールバック優先順を裏取りする。
- 完了報告や PR 作成の前に、下位層へ追加した処理が上位ランタイムから実際に呼ばれている結合点と、上記境界監査の結果を確認する。

## 原則

- 境界条件は有界性、停止順序、時間軸、原子性、認可とタイムアウトの 5 軸で点検する。
- 下位 API の追加だけでは完了とせず、上位ランタイムへの配線と結合検証までを実装完了の基準とする。
