# リポジトリの網羅的ドリフト監査と 2 段ファンアウト

リポジトリの文書・スキル・テスト資産がコードからずれていないか、重複や構造上の問題がないかを網羅的に洗い出す作業は、子セッションへの 2 段の振り分けで進める。
計画フェーズで各項目の計画書を集めてユーザーに採択させ、実装フェーズで採択項目を並列に実装させる。
ゴールは、洗い出しから修整までを一連の流れとして進めつつ、採否の判定をユーザーへ返す地点を一箇所に集約することである。

## 責任範囲の境界

- **実装フェーズの分割と依頼**：トラックの切り方、排他ファイル境界、子プロンプトの定型は `parallel-child-implementation` に従う。本スキルは監査固有の走査観点と 2 段構成だけを定める。
- **要協議の提示形式**：自律適用と要協議の切り分け、推奨案つき選択肢の形式は `requirements-definition` に従う。
- **レビュー対応**：実装子が受ける Devin Review 指摘のトリアージは `devin-review-triage` に委ねる。
- **起動と監視**：子セッションの作成、structured output、添付、待機の作法は builtin の `managing-child-sessions` と `dynamic-workflows` に委ねる。

## 走査観点

監査の第一走査で見る領域は次の 6 群である。リポジトリの構成に合わせて取捨選択する。

- **文書ドリフト**：状況記述行の陳腐化、構造図と節番号参照のずれ、廃止用語、README。
- **残課題帳簿との突合**：解消済みの項目と、直近の作業で未記録になった項目。
- **仕様 ID と実装の機械照合**：文書側の仕様 ID とコード側の ID トークンを正規表現で両方向に抽出し、死んだ仕様行・未登録 ID・同名衝突・改番に分類する。
- **スキル陳腐化**：`.devin/skills`、プラグインスキル、メモリの記述と現行コードの比較。UI や運用が変わった箇所を重点的に見る。
- **重複**：ファイル単位の重複、スケルトン構造の類似、CSS セレクタの共有化余地。
- **構造**：大きいファイルの責務評価。PR サイズに収まる分割だけを項目化し、全面再設計が要るものは項目にしない。

## 手順

1. 第一走査を自分で行い、候補項目を列挙する。各項目に、根拠となる証拠（ファイル、行番号、観測した症状）を添える。
2. 計画フェーズとして各項目を 1 子セッションへ割り当てる。子プロンプトは `child-prompts.md` の定型を使い、証拠は渡すが「現行 main で再検証してから使う」よう明記する。
3. 子から返った計画書を集約書 1 文書にまとめる。総表、推奨案つき要協議一覧、自律適用一覧、子の新規発見、実施順序と競合予測を含める。
4. ユーザーに採択を仰ぐ。採択された項目だけを実装フェーズへ進める。
5. 実装フェーズでは採択項目を 1 子 1 トラックで実装させる。同じファイルを触る項目が複数あるときは同一トラックへ再編してから割り当てる。計画書を正として添付し、`parallel-child-implementation` の定型に従う。完了条件は PR 作成、CI グリーン、Devin Review トリアージ、structured output 報告、自己 sleep までとする。
6. 子の structured output を回収し、PR 一覧と残課題をユーザーへ報告する。

## 設計の要点

- 渡した証拠は子に必ず再検証させる。親の走査は行番号ずれや誤検出を含みうる。子が証拠を訂正したり新規発見を加えたりすることを前提にした構成にする。
- 範囲外の発見は潰さず `out_of_scope_findings` で集約へ返させる。計画フェーズの副産物として拾う。
- Phase 番号、仕様決定 ID、テスト ID などの採番は計画書では仮採番と明記し、先行 PR のマージ後に確定する。並行して別の改修が進んでいると採番が衝突する。
- 複数 PR が同じファイルの別箇所を触るとき、集約書にマージ順と競合予測を添える。
- PR でない成果物（プラグイン更新、外部サービスの設定変更）は子に振らず親が直接行う。承認カードは親のセッションで出る必要がある。
- 計画書はリポジトリ外（`~/plans` など）に置く。監査の成果物は計画書と集約書、および実装子の PR であり、計画書自体をリポジトリに残さない。

## リファクタ系トラックの検証技法

挙動不変を謳う構造整理は、移動のみであることを機械的に示せるとレビューが早い。

- **行多重集合照合**：新旧ファイルの全行をソートした多重集合で diff を取り、追加行と削除行がないことを示す。行の増減がないことの証明であり、行の並べ替えによる挙動変更は検出できないため、移動単位の内部順序が保たれていることは別途差分で確認する。
- **A/B 実機比較**：ブランチ版とマージベースの worktree を並べ、同じ操作を通して出力が完全一致することを確認する。

## 原則

- 監査は証拠つきの候補列挙であり、第一走査で結論を確定しない。確定は子の再検証とユーザーの採択に任せる。
- 2 段構成の狙いは、洗い出し（広く浅い）と掘り下げ（狭く深い）を分けて、ユーザーが採否を決める地点を一箇所に集約することにある。
- 子が親の証拠を訂正することは設計どおりの動作である。訂正と新規発見は集約書の「子の発見」節に集める。
