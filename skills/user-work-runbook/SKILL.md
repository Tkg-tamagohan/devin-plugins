# ユーザー作業手順書の作り方

計画の一部がユーザーの手作業に割り当てられているとき、手順書はコードで確認した事実だけで組み立てる。
実在しない UI や未実装の機能を前提にした手順を書くと、手順書全体が信用を失う。

## 手順

1. 手順書の対象になる作業を、実装計画や要件定義から確定させる。
2. 使うことになる画面、バリデーション、エクスポート処理をコードで裏取りする。
   - 画面ファイル、サービス、ワークフローを読み、「できること」と「まだできないこと（未実装）」を分ける。
3. 旧版や姉妹リポジトリに同種の手順書がないか探し、あれば流用して書き直す。
4. 次の定型構成で書き、対象作業に該当しない項目は省く。
   - 作業分担表（Devin がやること／ユーザーがやること）
   - 準備物の棚卸し（データ、素材、命名規約）
   - 入力順序（参照される側から登録する）
   - 検証とエクスポート
   - 引き渡し（エクスポート物 → PR → デプロイ）
   - フィールド早見表
   - 注意点（ブラウザ内メモリのみなど、失われるものや全置換されるもの）
5. 手順書は添付ファイルで納品し、リポジトリへのコミットは提案に留める。

## 原則

- 手順の各ステップはコードで確認した画面名とボタン名で書き、未実装のものは「未実装」と明記して入力順序などの制約として組み込む。
- ユーザーが躓くポイント（失われるデータ、置換されるデータ、権限の要否）を注意点に集約する。
