# 理解のための出力形式の選択

説明、調査結果の報告、設計の解説など「ユーザーの理解」が目的の作業では、成果物の表現形式を意図的に選ぶ。
平文の散文を既定とせず、内容が許す限り表現力の高い形式へ上げる。
成果物は使い捨てのカスタムソフトウェアとして扱い、永続化や品質保証は求めない。

## 責任範囲の境界

- **日本語の文体**：`japanese-tech-writing` に従う。本スキルは文体を定めない。
- **HTML 成果物の作り方**：builtin の `interactive-artifacts` スキルに委ねる。本スキルは形式を選ぶ基準と納品の扱いだけを定める。

## 形式のはしご

下に行くほど表現力が上がり、作成コストも上がる。
既定の上限はインタラクティブ HTML であり、それより上の形式（動画、サーバーが要るアプリなど）はユーザーの明示指示があるときだけ使う。

1. **制約付き文章**：ASD-STE100（航空機整備文書向けの制限自然言語）の書き方の制約を借りた技術文。用語統一、一文一義、能動態、手順の番号化を適用する。完全準拠ではなく「STE の 8 割」程度の緩和版でよい。正確さが要る分量の多い説明に使う。
2. **図**：構造、依存関係、フロー、状態遷移が主題なら文章より図にする。SVG、Mermaid、または artifact キットの diagram テンプレートで作る。
3. **インタラクティブ HTML**：閲覧者が操作して理解するほうが速い内容（パラメータを動かす、絞り込む、段階的に開く）は、単一ファイルの HTML 成果物にする。

## 選択の基準

- 必要十分な、最も安い形式を選ぶ。短い回答に図や HTML は作らない。
- 迷ったら一段上げる。構造の説明が三段落を超えるなら図へ、図や表が五枚を超えるならインタラクティブ化を検討する。
- ユーザーが形式を指定した場合はそれに従う。指定がなければこのはしごで判断し、選んだ形式とその理由を一行で伝える。

## 成果物の扱い

- `message_user` の attachments で渡す。HTML、PDF、SVG はインラインで表示される。
- 使い捨てが前提：リポジトリにコミットしない、lint やテストを要求しない、命名や構造を磨かない。再利用を求められたときに初めて整備する。
- 使い捨て成果物のためだけの依存はリポジトリへ追加せず、VM ローカルにインストールして済ませる。
- ユーザー自身に操作してほしい成果物は `browser_preview` で見せる。

## 動画の明示指示があるとき

ユーザーが明示的に動画を求めた場合に限り作る（「3b1b 風の解説動画」など）。
手順は台本→場面ごとの映像生成（HTML/canvas アニメーション、manim、録画）→ ffmpeg による連結→ナレーション合成。
ナレーションは ElevenLabs 等の API キーがあれば使い、なければローカル TTS または無音字幕にフォールバックする。
使った音声手段とフォールバックを報告し、キーの新規発行が要る場合はユーザーに確認する。

## 原則

- 理解が目的の成果物では散文を既定にせず、必要十分な最上位の形式へ上げる。
- 成果物は使い捨てであり、品質保証や永続化は求めない。
- 既定の上限はインタラクティブ HTML とし、動画などそれより上の形式は明示指示があるときだけ作る。
