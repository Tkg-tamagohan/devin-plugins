# テストスイートの不要テスト走査と整理

肥大化や形骸化した既存テストスイートを棚卸しし、検証価値を失ったテストの削除、重複テストのパラメタライズ統合、孤立したテスト補助コードの掃除を進める。
ゴールは現行仕様と回帰防護網を維持したまま、保守コストと実行時間を下げることである。

## 責任範囲の境界

- **テストの新規作成と規約**：仕様準拠テストの記述、非同期の同期要件、テスト ID の採番、テスト結果表の形式はルール `test-conventions` に委ねる。
- **大規模リポジトリの並列実行**：多数のテストファイルへ並列走査と並列削除を振り分ける 2 段ファンアウトと排他ファイル境界の設計は `repo-drift-audit` に委ねる。
- **要協議の提示形式**：要協議候補への ID 付与、推奨案、選択肢比較の形式は `requirements-definition` に委ねる。
- **常駐システムの境界保護**：有界性、停止順序、時間軸、原子性、認可に関わる必須検証の観点は `systems-pre-pr-audit` を参照し、過剰テストと誤判定しないための保護基準に使う。

## 保護対象（削除や弱体化を行わないテスト）

走査時は最初に保護対象を特定し、次のいずれかに該当するテストは原則として「保持」に分類する。

- **仕様と要件に紐づくテスト**：仕様書、要件定義、受け入れ基準、または仕様 ID（例：`AUTH-01`）へ明示的に対応しているテスト。
- **過去の障害に対する回帰テスト**：`git log`、`git blame`、コメント、PR や Issue 番号によりバグ修正の再発防止と裏付けられるテスト。
- **重要な不変条件と境界を守るテスト**：セキュリティ、認可、境界値、並行性、停止順序、トランザクション整合性を検証するテスト。
- **唯一の検証経路となるテスト**：削除すると本番コードの到達可能な重要分岐を検証するテストが他に一切残らなくなるテスト。
- **役割の異なる多層テスト**：上位の結合テストと検証対象が重なって見えても、失敗箇所の局所化や高速な単体フィードバックという独立した役割を担うテスト。

## 3 区分への分類基準

保護対象に該当しない候補を、根拠と影響に応じて次の 3 区分へ仕分ける。
判断に迷う候補は自律適用せず、要協議へ寄せる。

### 自律適用（事前承認を待たず削除または安全に整理してよい候補）

次の安全条件をすべて満たし、かつ下の類型に該当するものだけを対象とする。

- **安全条件**：仕様書、現行コード、`git log` の裏取りで保護対象でないことを確認済みであり、現行仕様に対する検証網が減らず、かつ複数ファイルの広範な一括削除に当たらないこと。
- **廃止および削除済み機能のテスト**：対象の仕様や本番機能が完全に廃止済みであり、テスト専用コードしか呼んでいないか廃止理由が明記されたまま放置されているテスト。
- **空アサーションおよび恒真テスト**：アサーションが存在せず非パニックのスモーク検証としての意図も確認できないテスト、モックへ仕込んだ固定値をそのまま比較しているだけのテスト、恒真条件のみを検証するテスト。
- **完全重複テスト**：同一ファイルまたは同一レイヤ内で、同じ入力、同じ経路、同じ期待値を二重に実行しているテスト（テスト ID が異なる場合は要協議とする）。
- **検証範囲を変えない小規模統合**：同一ファイル内で、検証ケース、アサーション、テスト ID を一切変えずに重複記述をテーブル駆動やパラメタライズへまとめる整理。
- **明確に孤立したテスト補助コード**：テストを削除または統合した結果、どのテストからも参照されなくなったテスト専用のヘルパー、モック、フィクスチャ、スナップショットファイル。

### 要協議（根拠と推奨案を添えてユーザーの採択を仰ぐ候補）

- **包含関係にある冗長テスト**：別テストや上位テストに包含されるように見えるが、粒度、実行速度、失敗局所化にトレードオフがあるもの。
- **実装密結合テスト（変更検出テスト）**：非公開構造、過度なモック呼び出し回数、過大な完全一致スナップショットに依存するテスト。
  削除案だけでなく振る舞いテストへの書き換え案も併記して推奨を示す。
- **言語や型システム、外部ライブラリの自明挙動テスト**：実行時境界の防御や依存更新時の契約確認を意図している可能性があるもの。
- **意図不明の skip や ignore テスト**：廃止の裏取りができず、バグ修正待ち、Flaky 調査待ち、環境依存の可能性があるもの。
- **テスト ID の統廃合や複数ファイル跨ぎの統合**：仕様文書との対応更新や管理単位の変更を伴う整理。
- **大量ファイルの一括削除**：対象が複数ファイルの削除に及ぶ場合は、自律適用相当の候補であっても削除前に一覧でユーザーの確認を取る。

### 保持

保護対象に該当するもの、または裏取りの結果として独自の失敗モードを検出できると判明したテスト。

## 手順

1. **対象範囲と前提の確認**：走査対象のディレクトリ、テスト種別、仕様書の所在、テスト ID 規約の有無を確認する。
   対象テストファイルが多く単独走査が重い場合は、`repo-drift-audit` の 2 段ファンアウトへ切り替える。
2. **走査と履歴および仕様の裏取り**：候補ごとにファイル、行番号、テスト名や ID、不要と判断した症状を記録する。
   対象コード、仕様書、コメントに加え、`git log` と `git blame` で導入経緯を調べ、回帰テストや保留 Issue の有無を確認する。
3. **代替検証の確認**：現行の本番挙動を対象とする削除候補について、「本番コードの対象分岐を意図的に壊したとき、他のどのテストが失敗するか」をコード照合（利用可能ならカバレッジ差分や対象テスト単体除外での確認）で裏付ける。
   ただし、廃止済み機能のテストや、非パニックのスモーク検証としての意図もない空アサーションや恒真テストのように、仕様、現行コード、`git log` の裏取りにより現行仕様で残すべき検証対象自体が存在しないと確認できた候補は代替テストを要さず、自律適用の安全条件へ照らして判定する。
   現行の検証対象が残るにもかかわらず代替テストが特定できない候補、または残すべき検証対象が存在しないことの裏取りが不十分な候補は要協議または保持へ格上げする。
4. **3 区分への仕分け**：保護対象を除外したうえで、各候補を自律適用、要協議、保持へ分類する。
5. **自律適用の実施と要協議の提示**：ユーザーから事前の一覧確認のみを求められている場合と複数ファイルを一括削除する場合を除き、自律適用分を実施してテスト通過を確認する。
   その後、実施済みの自律適用一覧と、ID、根拠、代替カバレッジ、推奨案を添えた要協議一覧（形式は `requirements-definition` に従う）をユーザーへ提示する。
6. **採択分の反映と孤立補助コードの掃除**：ユーザーの採択に従い、削除とパラメタライズ統合を実行する。
   あわせて、どのテストからも参照されなくなったテスト専用ヘルパー、モック、フィクスチャ、スナップショット、テストデータファイルを掃除する。
   テスト削除の結果として本番コード側が未使用になった場合は勝手に削除せず、範囲外の報告項目として記録する。
7. **削除後の検証と報告**：lint、型チェック、全テストスイートを実行して全パスを確認する。
   最終報告では自律適用と採択適用の内訳、整理前後のテスト件数（計測できた場合は実行時間やカバレッジ差分）、掃除した補助資産、残課題（本番側の未使用候補や先送り項目）をまとめる。

## テスト統合と補助コード掃除の要点

- **テスト ID の維持**：`test-conventions` に従い ID が振られたテストをパラメタライズ統合する場合は、各ケースの ID をケース定義へ保持し、ID の廃止や改番が生じる場合は文書側の更新要否を要協議へ上げる。
- **テスト専用 export の確認**：テストのためだけに公開されていた補助関数やテスト用フラグが不要になった場合、本番公開 API に影響がないか確認したうえで整理または報告する。
- **本番コードとの境界**：本スキルの変更対象はテストコードとテスト専用補助資産に限定し、本番ロジックの削除やリファクタは範囲外として報告に留める。

## 原則

- テスト削除は回帰防護網を削る操作であるため、推測で消さず仕様、履歴、代替検証（現行仕様で残すべき検証対象自体が存在しないならその裏取り）の 3 点で裏取る。
- 境界が曖昧な候補、削除と書き換えの両論がある候補、大量ファイル削除は自律適用せず要協議へ寄せる。
- 自律適用で削除したテストであっても、後から復元や検証ができるよう根拠付きで一覧報告する。
- 重複テストの整理では検証範囲を減らさない統合を優先し、削除後の孤立したテスト補助資産まで同じ変更で片付ける。
