# UI における冗長なガイド文の排除

AI が画面やツールを生成すると、見出し直下の解説、自明な操作案内、挨拶バナーなどの過剰なガイド文が増えやすい。
画面の視認性と情報密度を保つため、ラベルやコントロール自体で伝わる箇所には説明文を置かず、ユーザーが判断や入力で迷う制約と副作用だけを残す。

## 責任範囲の境界

- **HTML 成果物の作成と形式選択**：出力形式の判断は `output-format-escalation` に、単一ファイル HTML の作成手順は builtin の `devin-artifact` に委ねる。
  本スキルは UI 上に表示する文言の要否と簡潔さだけを定める。
- **UI の先行確認**：ユーザー操作を伴う UI を実装して確認する順序はルール `ui-mock-first` に従う。
- **技術文書の文体**：ドキュメントや解説記事の推敲は `japanese-tech-writing` に委ねる。
  本スキルは画面上の見出し、ラベル、補助文、通知などの UI 文言を対象とする。

## 残す文言と削る文言の基準

見出し直下の説明文、リード文、使い方バナー、入力補助文を置く前に、次の五つの問いに照らす。
いずれにも当てはまらない解説文は配置しない。
エラー表示や現在の状態を示す通知（「通信に失敗しました」「項目がありません」など）は削除対象から外し、原因と次の対処だけを短く示す。

- **不可逆または破壊的な結果**：削除、公開、課金など、実行すると元に戻せない影響や周辺データへの波及を事前に知らせる必要があるか。
- **送信前に知り得ない制約**：文字数制限、許可する文字種や形式、上限サイズなど、入力規則を前もって示さないと失敗するか。
- **非自明な副作用や待ち時間**：保存と同時に外部へ通知が飛ぶ、反映に数分かかるなど、見た目から予測できない挙動があるか。
- **紛らわしい語の区別**：似た項目が並んでおり、ラベルだけでは指す対象を一意に決められないか（例：請求先メールと通知先メール）。
- **仕様や法令で必須の表示**：利用規約への同意や法的注記など、要件として掲示が求められているか。

## 削るべき典型パターンと書き換え例

### 見出しやカード直下の重複リード文

見出しやボタンを見れば用途が分かる箇所に、同じ意味の解説文を添えない。

```text
NG: 設定
    ここではアプリケーションの各種設定を変更できます。

NG: ユーザー一覧
    登録されているユーザーの一覧を表示・管理します。

OK: 設定（またはユーザー一覧）の見出しと中身だけを配置する
```

### ウェルカムバナーと操作手順の常設ガイド

画面上部に用途紹介や使い方の案内箱を置かず、主操作ボタンと入力欄の配置で次の行動を示す。

```text
NG: 〇〇管理ツールへようこそ！以下のフォームに入力して「保存」を押してください。
NG: まずは右上の「新規作成」ボタンから最初の項目を追加してみましょう。

OK: バナーを削り、入力欄と「保存」ボタン（または「新規作成」ボタン）だけを置く
```

### ラベル、プレースホルダー、補助文の重複

ラベルの言い換えを補助文に書かず、プレースホルダーには入力例の値だけを入れる。

```text
NG: ラベル: プロジェクト名
    placeholder: プロジェクト名を入力
    補助文: 作成するプロジェクトの名前を入力してください。

OK: ラベル: プロジェクト名
    placeholder: 例: ec-site-renewal
    補助文: 英小文字とハイフンのみ（制約がある場合のみ表示）
```

### 解説的な空状態

データがない画面に機能紹介や操作手順の長文を置かず、現在の状態と次の操作ボタンだけを置く。

```text
NG: まだデータがありません。新しい項目を作成するとここに一覧表示されます。
    右上の「新規作成」ボタンをクリックして始めましょう。

OK: 項目がありません  [新規作成]
OK: 一致する項目はありません  [条件をクリア]
```

### 冗長な確認ダイアログ

丁寧な前置きや操作手順の繰り返しを省き、対象と不可逆な影響だけを一文以内で伝える。

```text
NG: 本当に削除してもよろしいですか？この操作を実行するとデータが完全に削除され、
    元に戻すことはできませんのでご注意ください。

OK: 「project-alpha」を削除します。この操作は取り消せません。  [キャンセル] [削除]
```

### 機能 UI への飾り文句

抽象的な称賛の語を削り、対象物や状態を指す名詞に置き換える。

```text
NG: シームレスに一元管理 / 直感的なダッシュボード / 安心・安全なデータ保護
OK: 請求一覧 / 公開状態 / バックアップ設定
```

## 画面作成とレビューの手順

1. 画面構成を設計するとき、各ページやカードにリード文や使い方ボックスの枠を既定で設けない。
2. コンポーネントを実装したあと、画面に表示される説明文、リード文、補助文、バナー、通知文を抜き出す。
3. 説明文や案内文は「残す文言と削る文言の基準」に照らし、五つの条件のどれにも当たらないものを削る。
4. 残す文およびエラーや状態の通知文から「〜してください」「ここでは〜できます」のような前置きや操作案内を取り除き、状態、制約、結果だけを短く言い切る。
5. 既存の画面を改修するときも、既存仕様で固定された文言を除き、新しく追加する説明文に同じ基準を適用する。

## 原則

- 画面の文言は説明ではなく判断材料として置き、見出しやボタンを見れば分かることは書かない。
- 解説や案内として残すのは不可逆な結果、入力制約、非自明な副作用、紛らわしい語の区別、必須注記に限り、エラーや状態の通知は事実と対処だけを短く示す。
- 空状態と確認ダイアログは「状態または対象、影響、次の操作」だけを短く示す。
