# 要件定義の進め方

要件定義書、仕様書のドラフトを受け取った、または作成を求められたときは、以下の手順で進める。
目的は、仕様の空白をユーザーとの協議で埋め、確定した仕様と実装計画を文書として残すことである。
後続のセッションがその文書だけを読んで実装を再開できる状態をゴールとする。

## 責任範囲の境界

本スキルが扱うのは要件定義プロセスの進行と、成果物（要件定義書、決定記録、実装計画）の構造だけである。

- **文章の文体と整形**：日本語の文書を書いたり推敲したりするときは `japanese-tech-writing` を呼び出して従う。
  - 本スキルは文体ルールを定めない。
- **環境とプラットフォーム**：blueprint や実行環境の構築や不具合は該当スキル（Windows なら `windows-blueprint`）に委ねる。
  - 要件定義では「この機能はどの実行環境を必要とするか」を明記するに留める。
- **共通の振る舞い**：推測の明記、文書を仕様の正として扱うこと、依頼範囲への限定など、プラグインの AGENTS.md にある常時ルールは本スキルの前提であり、ここでは繰り返さない。
- **リポジトリ固有の規約**：作業対象リポジトリに AGENTS.md やリポジトリ内スキルがある場合はそちらに従う。

## レビューで指摘を洗い出す

ドラフトを受け取ったら、まず文書を修正せず、指摘を重要度で分類して返す。
観点は次の通り。

- **モデルの抜け**：エンティティ、属性、保存、削除、バージョン管理などライフサイクルの欠落。
  - 機能の裏側で必要になるがモデル化されていない対象（例：発電、レイアウト保存）が典型である。
- **ルールの未定義**：境界条件、例外系、優先順位、単位や丸め方、競合時の扱い。
- **矛盾と曖昧さ**：節をまたいだ用語と扱いの不一致、複数の解釈が可能な記述。
- **非機能の欠落**：配布形式、権利と規約面、テスト方針、性能の目安。

ドメイン知識に基づく指摘は、確認していない事実を「〜と推測する」「〜の可能性がある」と明示する。
ユーザーに「レビューだけ」と指示された場合は、反映の提案まで留めて文書を変更しない。

## 要協議と自律適用に切り分ける

レビューで挙がった指摘、およびレビュー bot（Devin Review 等）の指摘を、次の基準で二分する。

- **要協議（仕様判断）**：機能の範囲、ユーザー体験、業務とドメインのルール、外部に見える振る舞いを左右するもの。
  - 迷ったらこちらに寄せる。
- **自律適用（技術的改善）**：実装手段、内部構造、データ正規化、テスト方針、防御的な検証など、仕様の意図を変えずに品質を上げるもの。

切り分けの判断自体をユーザーが覆せるよう、どの指摘をどちらに分類したかは一覧で示す。

## 協議項目を推奨案付きで提示する

- 自律適用分は要件定義書へ直接反映して PR に出し、要協議分だけを一覧で提示する。
- 一覧は ID（A, B, C, …）を振り、各項目に推奨案とその根拠を一文で添える。
  - ユーザーが「推奨を受け入れ」と答えるだけで決定できる粒度にする。
- 既存の決定や仕様を継承（踏襲）する場合も、継承候補を項目ごとに提示して確認を取る。
  - 一括の踏襲を既定にしない。
- 推奨案を出せない項目は、出せない理由（情報不足、複数案が等価、等）を書く。
- ユーザーが詳細や再検討を求めた項目は、選択肢を「案・内容・メリット・デメリット」の比較表で提示し、推奨を併記する。

## 決定を文書に記録する

- 確定した判断は、要件定義書とは別の決定記録ファイル（例：`docs/decision-records.md`）に ID、項目、決定内容の表で残す。
  - 要件定義書の肥大化を防ぐため、決定記録は要件定義書内の節として持たない。
  - 要件定義書側には決定記録ファイルへの案内を残し、各決定は表の ID で参照する（他文書からは「仕様決定 M」のように表記）。
  - 決定をチャットのログだけに残さない。
- 確定内容は要件定義書本文の該当箇所にも反映し、本文と決定記録が矛盾しない状態にする。
- 未決の項目は決定ではないため決定記録には載せず、要件定義書側の TODO（未決事項）として明示する。
  - 確定した時点で決定記録に移し、暗黙の確定を防ぐ。

## 確定仕様を実装計画に分解する

仕様が確定したら、実装計画（例：`docs/implementation-plan.md`）に分解する。
含めるものは次の通り。

- **前提と環境**：プラットフォーム依存の明示（例：UI が WPF なら Windows 環境が必須で、計算ロジックは Linux でも検証可能、といった切り分け）。
- **構成**：プロジェクト構成と依存方向、データモデルの詳細、中核ロジックの入出力とアルゴリズム概要。
- **フェーズ別タスク**：おおむね 1PR 単位のフェーズに分け、各フェーズに受け入れ条件を書く。
- **引き継ぎ手順**：現在地の確認方法（マージ済み Phase、チェックリスト）、ブランチ規約、特定環境が必要な作業の明示。

進捗は計画書のチェックリスト（`[ ]` / `[x]`）で管理し、別セッションが文書だけで再開できる粒度にする。

## 原則

- 仕様の空白は自分で埋めず、必ず協議項目として提示する（AGENTS.md「欠けている情報を勝手に埋めない」に準拠）。
- 各協議項目には推奨案を添えて、ユーザーの判断コストを下げる。
- 確定した仕様と決定は文書に保存し、以後のセッションがその文書を仕様の正として作業できるようにする。
